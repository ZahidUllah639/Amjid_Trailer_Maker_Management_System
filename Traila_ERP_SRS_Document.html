1. INTRODUCTION

1.1 Purpose of the Document

This Software Requirements Specification (SRS) document provides a formal, comprehensive, and exhaustive specification of the software requirements for the Traila ERP application. It defines the functional behaviors, system architecture, database specifications, financial calculation models, hardware communication protocols, and non-functional engineering standards governing the system from initial boot to application teardown.

1.2 Scope of the Software System

Traila ERP is a purpose-built, offline-first Enterprise Resource Planning and Accounting System engineered specifically for heavy trailer/trolley manufacturers, agricultural vehicle fabricators, and body-maker commission workshops. The application automates the entire manufacturing, procurement, commercial sales, and financial management cycle, as deployed at Amjid Trailer Makers, Main Hazar Khwani Ring Road, Peshawar.

Key Operational Capabilities: Traila ERP integrates serial-tracked vehicle fabrication tracking, precise piece-rate and raw material job-costing, supplier dual-balance (Payable vs Advance) ledgers, labour wage ledgers, commercial sales contracts with profit auditing, personal Khata (Udhaar Bahi) credit tracking, multi-wallet treasury cash-flow, 58mm/80mm thermal receipt and A4 PDF printing, and native Windows WhatsApp dispatch automation.

  • Software Engineers & Maintainers: Consult Section 3 (System Architecture), Section 4 (Functional Requirements), Section 6 (Database Specifications), and Section 9 (Requirements Traceability Matrix) for implementation details.
  • Workshop Managers & Business Administrators: Review Section 2 (Overall Description), Section 4 (Modules 3-14), and Section 8 (Operational Use Cases) to understand operational workflows.

2. OVERALL DESCRIPTION

2.1 Product Perspective & Architectural Topology

Traila ERP operates as a standalone, zero-cloud-dependent native 64-bit Windows desktop software application. It utilizes a unidirectional reactive state architecture orchestrated via Flutter BLoC (ERPCubit), backed by an embedded SQLite database managed through Drift ORM.

3. EXTERNAL INTERFACE REQUIREMENTS

3.1 User Interfaces & Visual Design System

The application shell executes in Kiosk Mode (borderless, title bar controls removed, centered and auto-maximized to full display bounds).

  • Layout Structure: Responsive horizontal split featuring a collapsible dark slate navigation sidebar (260px expanded, 80px collapsed, background #1E293B) and a light content canvas (background #F8FAFC).
  • Ergonomic Spacing: Standard 29px (approx. 0.3-inch) separation between navigation and active module views.
  • Header Bar: Fixed 70px header housing a 300px search text field that instantly updates ERPState.searchQuery, dynamically filtering tables and lists without reload buttons.
  • Color Palette: Primary seed #2563EB (Royal Blue), background #FFFFFF, cards border #E2E8F0 with 12px rounded corners.
  • Typography: Google Fonts Inter applied globally across all UI widgets.

3.2 Hardware Interfaces: Thermal POS & Office Printers

  • Thermal Point-of-Sale (POS) Printers: Native spooling to 58mm (width 164 pt) and 80mm (width 226 pt) ESC/POS-compatible continuous receipt printers.
  • Office Laser / Inkjet Printers: Native spooling to standard A4 paper format (210mm x 297mm) via the Windows Print Spooler.
  • Luminance Thresholding: High-resolution color logos are dynamically downscaled to 300px width, converted to 8-bit grayscale, and thresholded ($L > 0.6 implies 255$, else $0$) to eliminate thermal print head ink-bleed.

3.3 Software Interfaces: Windows Desktop & Shell

  • Window Management: Managed via window_manager for borderless kiosk execution.
  • File System Access: path_provider maps persistent database storage to application support paths.
  • Shell Spooling: Direct process execution via Process.run('explorer.exe', ['/select,', filePath]) to bring the file manager to the foreground with the active invoice highlighted.

3.4 Communication Interfaces: WhatsApp Desktop Protocol

The application automates document delivery via WhatsApp without external paid APIs:

  1. The vector PDF is generated and serialized to %USERPROFILE%DocumentsTrailaInvoices<filename>.pdf.
  2. The telephone number is sanitized and converted to international E.164 format (Pakistani numbers starting with 03... or 10 digits are prepended with country code 92).
  3. The application executes cmd.exe /c start whatsapp://send?phone=<sanitizedNumber>, opening WhatsApp Desktop to the client chat.
  4. Simultaneously, Windows Explorer opens with the generated PDF selected for immediate drag-and-drop into the chat window.

4. SYSTEM FEATURES & FUNCTIONAL REQUIREMENTS

4.1 Module 01: Application Lifecycle & Kiosk Window Control

  • REQ-01-01: The application shall initialize the window_manager plugin on launch, strip all standard OS window decorations, center the window, and maximize it into kiosk mode.
  • REQ-01-02: The sidebar menu shall provide an Exit App action that invokes windowManager.close() to terminate the application cleanly.
  • REQ-01-03: The main shell shall manage page transitions via an unscrollable PageView controlled by currentModuleIndex with smooth curve animations (300ms duration).

4.2 Module 02: Drift Relational Storage & Self-Healing Engine

  • REQ-02-01: The database shall execute under schema version 11 with foreign key enforcement active (PRAGMA foreign_keys = ON).
  • REQ-02-02 (Self-Healing Balances): During loadData(), if any supplier or labourer record has remainingBalance == 0, openingBalance > 0, and zero prior transactions, the system shall automatically repair the database by setting remainingBalance = openingBalance.
  • REQ-02-03 (Legacy Invoice Backfill): The system shall scan legacy records and generate backfilled OPEN-BAL invoices for any entity possessing an opening balance lacking an invoice voucher.
  • REQ-02-04 (Legacy Sales Downpayment Backfill): The system shall inspect historical sales where paidAmount > 0 lacking downpayment vouchers, automatically generating synthetic records (DP-<saleId>-BACKFILL) in the payments ledger.

4.3 Module 03: Executive Dashboard & Workshop Fleet Metrics

  • REQ-03-01: The dashboard shall calculate and render live counts of manufactured trailers categorized into three mutually exclusive states: Pending Trailers, Ready Trailers, and Sold Trailers.
  • REQ-03-02: The dashboard shall calculate aggregate available cash across all registered accounts: $ ext{Total Balance} = sum ext{AccountBalance}_i$.
  • REQ-03-03: Active counter-party summaries shall display the total count of registered suppliers and total workshop labour workforce.
  • REQ-03-04: Quick action buttons shall enable single-click navigation to Traila Register (Index 1), Procurement (Index 2), Labour Work (Index 3), and Sales (Index 4).

4.4 Module 04: Traila Production & Fleet Management

  • REQ-04-01: The system shall support registering new trailer units with a mandatory manual identifier (e.g., T1, T-102) and Model Name.
  • REQ-04-02: Newly created trailers shall automatically be assigned status TrailaStatus.pending with initial totalManufacturingCost = 0.0.
  • REQ-04-03: The system shall support modifying trailer metadata (ID, Model Name, Registration Date).
  • REQ-04-04: The system shall allow transitioning trailer status between pending (under construction), ready (available for commercial sale), and sold.
  • REQ-04-05: Deletion of a trailer unit shall cascade delete all associated expenses, preventing orphan records.

4.5 Module 05: Manufacturing Cost & Job-Costing Engine

  • REQ-05-01: The Unit Manufacturing Cost ($C_{ ext{Traila}}$) shall be calculated dynamically as: $$C_{ ext{Traila}} = sum M_{ ext{Materials}} + sum W_{ ext{Labour}} + sum E_{ ext{Overhead}}$$
  • REQ-05-02: Any procurement bill or labour entry linked to a trailer ID shall trigger _syncTrailaTotalCost(trailaId), updating the persisted cost in the Trailas table.
  • REQ-05-03: Manual overhead expenses (e.g., permits, specialized transport) can be added directly to any trailer unit via the Traila History interface.

4.6 Module 06: Supplier Procurement & Materials Registry

  • REQ-06-01: The system shall maintain a supplier directory capturing Manual ID, Name, Phone Number, Shop Name, Market Location, Address, WhatsApp Number, and Initial Opening Balance.
  • REQ-06-02: Purchase bills shall capture: Bill Number (auto-generated INV-SP-XXXX if blank), Bill Date, Target Traila ID (optional), Multi-item lines (Name, Quantity, Unit Price, Total), Upfront Payment Amount, and Source Account.
  • REQ-06-03: Line total and bill total shall compute as: $ ext{LineTotal} = ext{Qty} imes ext{UnitPrice}$, $ ext{BillTotal} = sum ext{LineTotal}_i$.

4.7 Module 07: Supplier Financial Ledger & Dual-Balance Settlements

  • REQ-07-01 (Dual-Balance Logic): Supplier net balance evaluates according to: $$ ext{Net} = ext{OpeningBalance} + sum ext{Purchases} - sum ext{Payments}$$ If $ ext{Net} ge 0 implies ext{RemainingBalance} = ext{Net}$ (Payable debt owed to supplier).
    If $ ext{Net} < 0 implies ext{AdvanceBalance} = | ext{Net}|$ (Advance credit balance held by supplier).
  • REQ-07-02 (Snapshot Integrity): Invoice generation shall snapshot the pre-transaction balance from the database and store it directly in invoices.previousBalance.
  • REQ-07-03 (Split Payments): The system shall support split-disbursements across multiple accounts simultaneously (e.g., Rs. 50,000 Cash + Rs. 150,000 Bank).
  • REQ-07-04: Every supplier payment disbursement shall post a debit transaction (type: take) to the designated financial wallet.

4.8 Module 08: Labour Workforce & Piece-Rate Job Work

  • REQ-08-01: The system shall maintain a labour workforce directory recording Worker ID, Name, Phone, WhatsApp, Home Address, and Opening Balance.
  • REQ-08-02: Work orders shall capture: Entry Number (auto-generated INV-LW-XXXX if blank), Target Traila ID, Task Description (e.g., "Chassis welding", "Double axle fitting"), Piece-rate Charge, and optional Upfront Wage Payment.
  • REQ-08-03: Upfront payments logged during work order entry shall automatically generate a linked payment voucher (LPAY-...), debit the chosen wallet, and adjust the worker's balance.

4.9 Module 09: Labour Financial Ledger & Wage Disbursements

  • REQ-09-01: Worker payable wage balance evaluates according to: $$ ext{Wage Due} = ext{OpeningBalance} + sum ext{Work Charges} - sum ext{Wages Paid}$$
  • REQ-09-02: Wage disbursement vouchers shall generate sequential receipt numbers (INV-L-PAY-XXXXX).
  • REQ-09-03: Deleting or modifying a wage payment shall execute _syncLabourBalances(labourId) to recalculate running balances.

4.10 Module 10: Finished Unit Sales & Commercial Contracts

  • REQ-10-01: Only trailer units possessing status TrailaStatus.ready shall be eligible for commercial sale.
  • REQ-10-02: Sale contract creation shall capture: Ready Unit Selection, Buyer Profiling (Name, Phone, CNIC, Address, WhatsApp), Agreed Sale Price ($P_{ ext{Sale}}$), Initial Downpayment, Target Wallet, and Sale Date.
  • REQ-10-03 (Internal Profit Engine): The system shall compute gross operational unit profit: $$ ext{Profit} = P_{ ext{Sale}} - C_{ ext{Manufacturing}}$$ This figure is strictly retained for management auditing and shielded from customer documents.
  • REQ-10-04: Contract execution shall update the trailer's status in Trailas to 'sold' and store salePrice.
  • REQ-10-05: Sales shall generate unique commercial sequence receipts formatted as SALE-XXXXX.

4.11 Module 11: Sale Installments & Buyer Global Debt Consolidation

  • REQ-11-01 (Consolidated Debt Tracking): When generating a sale invoice or installment receipt, the system shall aggregate all unpaid debts from all other trailers purchased by the same buyer: $$ ext{Global Previous Debt} = sum_{s in ext{Sales}_{ ext{Buyer}} setminus {s_{ ext{current}}}} ext{RemainingBalance}(s)$$ $$ ext{Gross Total Due} = P_{ ext{Sale}} + ext{Global Previous Debt}$$
  • REQ-11-02: Subsequent installment payments shall be tracked in the payments ledger, updating remaining debt and posting an incoming cash transaction (type: add).
  • REQ-11-03: Sales Management shall provide segregated views: Ready for Sale, Partial / Pending, and Fully Paid.

4.12 Module 12: Khata (Customer & Personal Credit Ledger)

  • REQ-12-01: The system shall provide an independent Khata subsystem for tracking general counter-party credits, advances, and customer accounts (Udhaar Bahi).
  • REQ-12-02: Transactions shall be categorized as KhataTransactionType.cashOut (debit, increases debt owed to business) or KhataTransactionType.cashIn (credit, decreases debt).
  • REQ-12-03 (Account Sync Toggle): Each transaction features a syncToAccount flag: - If enabled: Debits or credits the designated commercial account wallet concurrently.
    - If disabled: Updates the personal ledger without altering physical cash balances.
  • REQ-12-04: Khata running balance calculates as: $ ext{Balance} = ext{Opening} + sum ext{CashOut} - sum ext{CashIn}$.

4.13 Module 13: Cash Flow, Multi-Wallet Treasury & Transfers

  • REQ-13-01: The system shall support creating multiple commercial liquidity wallets (e.g., Cash In Hand, Meezan Bank, HBL, EasyPaisa).
  • REQ-13-02: Inter-account fund transfers shall execute as an atomic transaction creating two linked entries: 1. A debit entry on source account (type: transfer, id: TRF-...-OUT).
    2. A credit entry on destination account (type: transfer, id: TRF-...-IN).
    3. Both entries share an identical linkedTransferId.
  • REQ-13-03: Modifying or deleting a transfer transaction shall automatically reconcile the reciprocal twin entry.

4.14 Module 14: Profit & Loss (P&L) Financial Engine

  • REQ-14-01: The P&L engine shall filter financial metrics across temporal boundaries: All Time, Monthly, Yearly, and Custom Date Range.
  • REQ-14-02: Financial engine metrics evaluation: $$ ext{Total Revenue} = sum_{s in ext{Sales} cap ext{Range}} s. ext{salePrice}$$ $$ ext{Total Expenses} = sum_{t in ext{Trailas} cap ext{Range}} t. ext{totalManufacturingCost}$$ $$ ext{Net Operating Profit} = ext{Total Revenue} - ext{Total Expenses}$$

  • REQ-16-01: The system shall interface directly with the Windows Print Spooler via printing: ^5.14.2.
  • REQ-16-02: Color bitmap assets printed to thermal paper shall be processed via monochrome luminance thresholding ($L le 0.6 implies ext{Black}$, else $ ext{White}$) to guarantee sharp printing without smudges.
  • REQ-16-03: The system shall provide an autoPrint configuration toggle to trigger printing automatically upon completing a sale.

5. NON-FUNCTIONAL REQUIREMENTS

5.1 Performance Requirements

  • NFR-PERF-01 (Query Execution Latency): Local SQLite database queries executed by loadData() shall execute in under 150ms for datasets up to 50,000 records.
  • NFR-PERF-02 (PDF Rendering Speed): Vector PDF rendering for multi-page statements or thermal receipts shall complete in under 350ms.
  • NFR-PERF-03 (UI Frame Rate): The user interface shall maintain a consistent 60 FPS on dual-core x86_64 desktop systems with 4 GB RAM. Global search query filtering shall evaluate without keystroke lag.

5.2 Reliability & Fault Tolerance

  • NFR-REL-01 (ACID Transaction Atomicity): Multi-table operations (e.g., trailer sales touching 7 tables) shall execute inside an atomic _db.transaction(). Any unexpected runtime failure shall cause a complete rollback with zero corrupted data.
  • NFR-REL-02 (Offline-First Execution): The system shall execute 100% of all computational, database, reporting, and printing workflows offline with zero cloud dependency.

5.3 Data Integrity & Security

  • NFR-SEC-01 (Foreign Key Enforcement): Foreign key constraints (PRAGMA foreign_keys = ON) shall be enforced on every database connection open.
  • NFR-SEC-02 (Cascading Integrity): Deleting a trailer shall cascade delete child TrailaExpenses and set linked invoices to null. Deleting a sale shall cascade delete linked installment records.
  • NFR-SEC-03 (SQL Injection Immunity): All database queries shall utilize Drift's type-safe parameterized query builder, guaranteeing complete immunity to SQL injection vulnerabilities.

5.4 Usability & Human Factors

  • NFR-USE-01: The application shall operate in kiosk mode to maximize screen area for workshop environments. All numeric inputs shall feature automatic validation and formatting.
  • NFR-USE-02: Financial amounts shall consistently display the currency prefix Rs. with clean number formatting.

7.1 Traila Manufacturing Cost Aggregation Algorithm

C_{ ext{Traila}} = sum_{m in M} ext{Amount}_m + sum_{w in W} ext{Amount}_w + sum_{e in E} ext{Amount}_e 
Future<void> _syncTrailaTotalCost(String trailaId) async {
  final expenses = await (_db.select(_db.trailaExpenses)
    ..where((t) => t.trailaId.equals(trailaId))).get();
  final totalCost = expenses.fold<double>(0.0, (sum, e) => sum + e.amount);

  await (_db.update(_db.trailas)..where((t) => t.id.equals(trailaId))).write(
    TrailasCompanion(totalManufacturingCost: Value(totalCost)),
  );
}

7.3 Double-Entry Inter-Account Fund Transfer

B_{ ext{Source, New}} = B_{ ext{Source, Current}} - ext{Amount} \ B_{ ext{Dest, New}} = B_{ ext{Dest, Current}} + ext{Amount} 
await _db.transaction(() async {
  // 1. Post Debit to Source Account
  await _db.into(_db.transactions).insert(TransactionsCompanion.insert(
    id: '$transferId-OUT', accountName: fromAccount.name,
    type: TransactionType.transfer.name, amount: amount,
    person: toAccount.name, description: 'Transfer OUT to ${toAccount.name}',
    date: date, category: 'Transfer', linkedTransferId: Value(transferId),
  ));
  // 2. Post Credit to Destination Account
  await _db.into(_db.transactions).insert(TransactionsCompanion.insert(
    id: '$transferId-IN', accountName: toAccount.name,
    type: TransactionType.transfer.name, amount: amount,
    person: fromAccount.name, description: 'Transfer IN from ${fromAccount.name}',
    date: date, category: 'Transfer', linkedTransferId: Value(transferId),
  ));
  // 3. Atomically update balances
  await (_db.update(_db.accounts)..where((t) => t.name.equals(fromAccount.name)))
      .write(AccountsCompanion(balance: Value(fromAccount.balance - amount)));
  await (_db.update(_db.accounts)..where((t) => t.name.equals(toAccount.name)))
      .write(AccountsCompanion(balance: Value(toAccount.balance + amount)));
});

for (final pixel in processedImage) {
